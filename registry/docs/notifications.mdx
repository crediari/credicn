This guide describes a reusable foundation for notifications in internal systems.
[`NotificationCenter`](/components/notification-center) provides the interface, while the application
remains responsible for authorization, persistence, delivery, and navigation.

<Callout title="Core principle">
  Separate notification content from each recipient’s delivery state. A notification can have
  multiple recipients, but each person has their own read status.
</Callout>

## Data Model

The example below uses Prisma as a reference. The same separation works with any relational
database.

```prisma
enum NotificationTone {
  DEFAULT
  INFO
  SUCCESS
  WARNING
  ERROR
}

enum NotificationChannel {
  IN_APP
  EMAIL
  PUSH
}

model Notification {
  id          String   @id @default(uuid())
  eventKey    String
  title       String
  description String?
  tone        NotificationTone @default(DEFAULT)
  action      Json?
  metadata    Json?
  dedupeKey   String?  @unique
  createdAt   DateTime @default(now())
  expiresAt   DateTime?

  recipients NotificationRecipient[]

  @@index([createdAt])
  @@index([eventKey, createdAt])
}

model NotificationRecipient {
  id             String       @id @default(uuid())
  notificationId String
  notification   Notification @relation(fields: [notificationId], references: [id], onDelete: Cascade)
  userId         String
  readAt         DateTime?
  archivedAt     DateTime?
  deliveredAt    DateTime?

  @@unique([notificationId, userId])
  @@index([userId, readAt, notificationId])
  @@index([userId, archivedAt, notificationId])
}

model NotificationPreference {
  id        String @id @default(uuid())
  userId    String
  eventKey  String
  channel   NotificationChannel
  enabled   Boolean @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([userId, eventKey, channel])
  @@index([userId, channel])
}
```

`eventKey` should represent a stable event, such as `ticket.assigned` or `comment.mentioned`.
Avoid adding a boolean column for each new preference: the `eventKey + channel` combination
can evolve without a migration for every event type.

`action` should contain declarative data, such as `{ "type": "ticket", "ticketId": "..." }`.
The frontend maps this contract to navigation. Do not store callbacks, executable HTML, or
unvalidated external URLs.

## Creation and Delivery

A business operation should produce an event without depending on UI details. The recommended
flow is:

1. Complete the business change and record an event or outbox entry in the same transaction.
2. Resolve recipients on the backend, respecting current scope and permissions.
3. Check preferences by `eventKey` and channel.
4. Create `Notification` and `NotificationRecipient` for the in-app channel.
5. Queue email or push delivery outside the main transaction.
6. Publish a real-time signal only after the commit.

Use a `dedupeKey` when the producer may repeat an event. For critical flows, prefer the outbox
pattern over a direct email or WebSocket call: an external failure then leaves the main operation
intact, and delivery can be retried safely.

## HTTP Contract

A small API is usually enough:

| Method  | Route                                                  | Purpose                                   |
| ------- | ------------------------------------------------------ | ----------------------------------------- |
| `GET`   | `/api/notifications?status=unread&cursor=...&limit=30` | Paginated list for the authenticated user |
| `GET`   | `/api/notifications/unread-count`                      | Lightweight header counter                |
| `PATCH` | `/api/notifications/:id/read`                          | Mark a notification as read               |
| `POST`  | `/api/notifications/read-all`                          | Mark eligible notifications as read       |
| `GET`   | `/api/notification-preferences`                        | Effective user preferences                |
| `PUT`   | `/api/notification-preferences/:eventKey/:channel`     | Update a preference                       |

Never trust a browser-supplied `userId` as authority. Resolve the user from the session and scope
every update with `WHERE userId = session.user.id`. Return `404` for both missing items and items
owned by someone else to avoid revealing their existence.

Example of a normalized response:

```json
{
  "items": [
    {
      "id": "notification-id",
      "title": "New ticket assigned",
      "description": "Ticket #4821 needs an initial response.",
      "tone": "info",
      "createdAt": "2026-09-29T17:56:00.000Z",
      "read": false,
      "metadata": "Support",
      "action": { "type": "ticket", "ticketId": "4821" }
    }
  ],
  "nextCursor": null,
  "unreadCount": 1
}
```

Use cursor pagination based on `(createdAt, id)`. Offset pagination becomes expensive and can
duplicate or skip records as new notifications arrive.

## Query Hook

With TanStack Query, keep queries and mutations outside the visual component:

```tsx
function useNotifications() {
  const queryClient = useQueryClient();
  const queryKey = ["notifications"] as const;

  const query = useQuery({
    queryKey,
    queryFn: listNotifications,
    staleTime: 30_000,
    refetchInterval: 60_000,
  });

  const markAsRead = useMutation({
    mutationFn: (id: string) => api.markNotificationAsRead(id),
    onMutate: async (id) => {
      await queryClient.cancelQueries({ queryKey });
      const previous = queryClient.getQueryData(queryKey);
      queryClient.setQueryData(queryKey, (current) => markReadLocally(current, id));
      return { previous };
    },
    onError: (_error, _id, context) => {
      queryClient.setQueryData(queryKey, context?.previous);
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey }),
  });

  return { ...query, markAsRead };
}
```

Apply the same optimistic update to the header counter. On failure, restore the previous snapshot
and show feedback; do not leave a notification visually marked as read when the server rejected
the operation.

## Real-Time Delivery and Synchronization

SSE is a good option when the browser only receives events. WebSocket makes sense when the app
already uses bidirectional communication. In either case, send a small event containing the ID or
an invalidation signal, then fetch the API again as the source of truth.

- Reconnect with backoff and jitter.
- Refetch when focus or connectivity returns.
- Keep polling as a fallback when real-time delivery is unnecessary.
- Do not blindly increment the counter: events can be duplicated or arrive out of order.
- Synchronize tabs with `BroadcastChannel` or shared invalidation when appropriate.

## Preferences

Set server defaults so new users get predictable behavior. Distinguish between:

- Editable preferences, such as product news and routine updates.
- Mandatory communications, such as security and outages, which should appear disabled in the UI
  with an explanation.
- Independent channels (`IN_APP`, `EMAIL`, `PUSH`). Disabling email should not implicitly disable
  in-app notifications.

The preferences endpoint should return the effective state, including defaults that have not yet
been stored in the database. Roll back the `Switch` visually when persistence fails.

## Security, Privacy, and Operations

- Render messages as text. If rich text is essential, sanitize it on both the server and client
  using a small allowlist.
- Keep secrets and sensitive data out of WebSocket payloads, logs, and push messages.
- Revalidate authorization when an action opens; receiving a notification does not grant permanent
  access to the resource.
- Define retention and cleanup rules for old and expired notifications.
- Track creation, delivery, failure, read, and queue-size metrics.
- Test user isolation, deduplication, concurrent reads, preference defaults, reconnection, and
  optimistic rollback.

## Connecting Data to the Component

```tsx
<NotificationCenter
  notifications={query.data?.items ?? []}
  preferences={preferencesQuery.data ?? []}
  loading={query.isPending}
  error={query.error?.message}
  pendingNotificationIds={markAsRead.isPending ? [markAsRead.variables] : []}
  markingAllAsRead={markAllAsRead.isPending}
  onRetry={() => query.refetch()}
  onMarkAsRead={(notification) => markAsRead.mutateAsync(notification.id)}
  onMarkAllAsRead={() => markAllAsRead.mutateAsync()}
  onPreferenceChange={(preference, enabled) =>
    updatePreference.mutateAsync({ id: preference.id, enabled })
  }
  onNotificationOpen={(notification) => openNotificationAction(notification.id)}
/>
```

The component derives its counter from `notifications`. If the header only queries a count
endpoint, load at least the unread notifications when opening the dialog to reconcile the value
before rendering the list.
